# Channel creation API

`POST /channels` creates a channel in the selected workspace. The request body is strict JSON with `name`, `visibility` (`public` or `private`), and an optional `description` (up to 500 characters). Names are trimmed, lowercased, and restricted to ASCII letters, digits, hyphens, and underscores (1–80 characters). The optional `Idempotency-Key` header must contain one non-empty value of at most 128 characters.

The endpoint resolves a verified Google identity from the Better Auth session and checks membership in the workspace named by `X-Workspace-Id`. The header selects a workspace but does not grant access; the server verifies membership before every operation. The creator ID always comes from the authenticated session. A successful response is `201` with `channel` and `creatorMembership`; the creator is persisted as a channel admin in the same Mongo transaction as the channel. Successful creation emits a structured `channel.created` audit log containing actor, target, workspace, channel ID, timestamp, and outcome; it contains no message content or credentials.

Stable errors are `unauthenticated` (401), `workspace_access_denied` (403), `validation_error` (400), `channel_name_conflict` (409), `idempotency_key_reused` (409), and `channel_storage_unavailable` (503). Reusing an idempotency key with the same normalized name and visibility replays the original response. Reusing it with different input returns `idempotency_key_reused`. Active channel names are unique inside a workspace; archived channel names may be reused.

## Persistence migration and operations

Run `pnpm --filter @workspace/api channels:initialize` as a deployment migration before enabling channel writes and browsing. It installs strict JSON Schema validators and named indexes for `channels`, `channel_memberships`, and `channel_creation_requests`. The indexes enforce active workspace-scoped channel names, support workspace/visibility/name browsing, provide efficient member channel listing, and enforce workspace/actor/idempotency-key uniqueness. The API checks migration state before writes and returns `channel_storage_unavailable` if the required validators or indexes are missing or differ from the expected definitions.

`GET /channels/:channelId` returns the channel details only to an active channel member in the selected workspace. Unauthenticated requests receive `unauthenticated`; users without membership in the selected workspace receive `workspace_access_denied`; non-members and channels outside the selected workspace receive the same `route_not_found` response to avoid disclosing private channel existence. Responses use `Cache-Control: no-store`.

`GET /channels` returns a bounded page of active channels in the selected workspace, ordered by normalized name. `scope=joined` (the default) returns channels the signed-in user belongs to, including private channels. `scope=discoverable` returns public channels the user has not joined; private channels are excluded server-side. `limit` defaults to 25 and accepts values from 1 to 50. `cursor` is an opaque, scope-bound keyset cursor returned as `nextCursor`; omit it for the first page. Invalid cursors and out-of-range limits return `validation_error`. Every page includes `channels` and `nextCursor` (`null` when exhausted) and uses `Cache-Control: no-store`. `GET /channels/:channelId` remains member-only, so discovering a public channel does not grant access to its details.

Creation uses a Mongo transaction across those three collections. The MongoDB deployment must be a replica set or sharded cluster that supports transactions; a standalone server is unsupported and produces `channel_storage_unavailable`. The runtime database account needs read/write access, while the initializer additionally needs collection and index administration privileges. Existing active duplicate names must be resolved deliberately before creating the unique index. The migration does not rewrite existing documents. The optional description field is accepted by the validator when present and is nullable; existing documents without the field remain readable.

## Membership lifecycle

`POST /channels/:channelId/memberships` joins an active public channel in the selected workspace. The API derives the user from the authenticated identity and verifies the selected workspace membership; repeated joins return the existing membership. Joining a private channel returns `channel_join_not_allowed` (403), and an unavailable or out-of-workspace channel returns the same `route_not_found` response used by member-only channel access.

`DELETE /channels/:channelId/memberships` removes the caller's membership; repeating the request is successful and idempotent. Leaving does not delete the channel or its retained data. The last admin may leave; the channel remains active and any other members retain access even if no administrators remain. Both endpoints use Mongo transactions and return `Cache-Control: no-store`. A per-channel `membershipRevision` write serializes membership changes; the field is optional so existing channel documents remain valid until their next membership mutation. Run `pnpm --filter @workspace/api channels:initialize` against the configured database after deploying this membership schema, then restart the API before testing joins or leaves; writes remain unavailable until the installed validators match the current definitions.

A self-leave atomically deletes the caller's membership and appends a typed
`system` / `member_left` history entry containing the authenticated member's
display name and leave time. It has no `senderId` or `sender`, is delivered to
the remaining channel room members as `channel:system:new`, and creates
`channel_member_left` notifications for the remaining members. Joining, inviting,
admin removal, and metadata updates also notify current members other than the
actor. `PATCH /channels/:channelId` accepts strict `{ "name": "...",
"description": "..." | null, "visibility": "public" | "private" }` JSON and
requires a channel admin. See the [API README](../../README.md#in-app-notifications)
for notification response, read, deduplication, mention, and realtime contracts.

Channel details and message history are member-only: public discovery alone grants neither. `GET /channels/:channelId/messages` returns the newest 50 messages in chronological order, with an optional opaque `before` cursor and a `limit` from 1 to 100. The returned `nextCursor` loads older messages; message ordering uses creation time and message ID as a stable tie-breaker. `POST /channels/:channelId/messages` accepts strict JSON containing only `text`, with 1–4,000 Unicode code points after whitespace validation. Both endpoints require a signed-in workspace member and current channel membership and use `Cache-Control: no-store`. The sender is always the authenticated user; responses include display name and avatar, never email. Missing profile data displays as “Former member.” Message sends and membership changes serialize through a channel revision write; reads check membership with the history query. Message text is never included in ordinary application logs.

Messages are retained when a user leaves or loses membership. An inaccessible channel returns the same privacy-safe `route_not_found` response as channel details. Archived channels remain readable to their members, but cannot accept new messages. Authenticated Socket.IO subscriptions deliver persisted messages and membership/list updates to authorized channel and workspace rooms. The message history REST API remains authoritative; on reconnect the client re-subscribes and reloads history to recover events missed while offline.

`pnpm --filter @workspace/api channels:initialize` now also installs the strict `channel_messages` collection validator and the `channel_messages_chronological` and `channel_messages_text` indexes. Deploy this API version and run the initializer before enabling messaging or search against an existing database. The runtime account needs read/write access; the initializer additionally needs collection and index administration privileges. Transaction-backed sends require a MongoDB replica set or sharded cluster. Initialization failure must be corrected before use; the API returns `channel_storage_unavailable` when the message migration is absent or its validator/index differs from the expected definition.

`DELETE /channels/:channelId/messages/:messageId` accepts strict JSON `{ "scope": "me" | "everyone" }` and returns `204 No Content`. `me` persists a per-user hide for any current channel member; hidden messages are excluded from that member's history, search results, and attachment downloads but remain visible to everyone else. `everyone` is allowed only to the message author or a workspace administrator, and still requires current workspace and channel membership. It physically removes the message, cleans up private Cloudinary attachments, and emits `channel:message:deleted` with `{ "channelId": "...", "messageId": "..." }` to the authorized channel room. Cleanup failures return `message_delete_cleanup_failed` rather than success; the error explicitly states that the message deletion was committed, and the deletion event is still broadcast. Personal hides do not emit a realtime event; the requesting client removes the message locally and subsequent history requests remain filtered. Run `channels:initialize` after deploying the validator change.

## Private-channel member management

`GET /channels/:channelId/memberships` lists members of a private channel to its current members. `POST /channels/:channelId/invitations` accepts `{ "email": "..." }`; only channel admins can add a target, and the target must have an existing account and membership in the same workspace. Duplicate additions return the existing membership and do not create a second membership or notification. Workspace invite links, rather than channel invites, are used to onboard people who are not yet workspace members.

`DELETE /channels/:channelId/memberships/:userId` lets a channel admin remove a regular member. Non-admins cannot invite or remove members, and admin targets cannot be removed; an admin can leave voluntarily through the self-leave endpoint, including when they are the last admin. As requested, the channel remains available to its remaining members without an admin. No administrator is automatically promoted, so member-management actions are unavailable until an admin rejoins or a future ownership-management flow is added. Unauthorized and unavailable channel/member lookups use the privacy-safe `route_not_found` response; attempts to remove an admin return `channel_membership_conflict`.

Membership updates are serialized through the channel revision transaction. Channel creation, default-channel provisioning, joins, leaves, invites, and removals emit structured audit events with actor, target, channel, workspace, timestamp, and outcome; no message content or email is written to the audit event. Removal deletes only the membership, leaving messages and authorship unchanged. Subsequent HTTP access checks observe the membership change immediately. Socket.IO connections authenticate with the Better Auth session, authorize workspace and channel subscriptions against current membership, and revoke channel-room access when channel membership changes. See [REALTIME.md](./REALTIME.md) for the event flow, security boundaries, client behavior, and deployment limitations.

Rollback can disable channel writes and drop the named indexes, then restore/remove the validators using `collMod`; preserve channel data unless a separately reviewed data migration requires cleanup. No live database migration was run as part of this implementation.
